# BDR-051 — Monitoring heartbeat Kuma plutôt que notifications

**Décision** : L'item « Notifications (playlist prête, échec de génération) » de la ROADMAP est remplacé par un heartbeat Uptime Kuma : push monitor « Mon Daily » sur le RPi perso (pas le NAS, qui est au travail), exposé via Tailscale Funnel limité à `/api/push`, intervalle 90 000 s (24 h + 1 h), retries 0, alerte Telegram. En fin de run, `pingUptime` dans `supabase/functions/generate-daily/index.ts` envoie `status=up`, ou `status=down` + raison si un compte échoue ou si un Daily sort sans podcast (cas du 429 Spotify). Le crash complet et le cron muet sont couverts par l'absence de heartbeat. Secret `UPTIME_PUSH_URL` absent = pas de ping. Ping uniquement côté Deno (pas dans `scripts/generate.ts`).

**Pourquoi** : Le besoin réel est de savoir quand le système déraille, pas de prévenir l'utilisateur chaque matin. Une notification émise par la fonction ne couvre pas le crash total (`546 WORKER_RESOURCE_LIMIT` déjà vu), contrairement à un heartbeat dont le silence déclenche l'alerte.

**Alternatives considérées** : Web Push PWA (`push_subscriptions`, VAPID, service worker en `injectManifest`), à reprendre si l'app s'ouvre à d'autres utilisateurs ; e-mail Resend ; ntfy ; bot Telegram direct ; Healthchecks.io (même principe, hébergé). Kuma retenu car déjà en place sur le RPi avec Telegram branché.
